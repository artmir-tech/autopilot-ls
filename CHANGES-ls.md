# autopilot-ls — fork of Autopilot for long, nearly autonomous projects

**In English, briefly.** `autopilot-ls` is a fork of the [Autopilot](https://github.com/nick-vels/skills) skill for Claude Code (base: Autopilot 2.2.3, commit `5ed4b79`), for projects of many weeks that run nearly unattended; it was born on the rebuild of «Легко Сказать», a Russian-language Telegram coaching bot. It keeps Autopilot's core — the verbatim-brief manifest, the four gates, the blind acceptance — and adds: a model and an effort per ticket with an escalation ladder; a git worktree per executor and commits limited to the ticket's files; Uncle Bob's [ub-mode](https://github.com/unclebob/ub-mode) as the executors' code standard with deterministic gates (CRAP, duplication, mutation) that block on their own; prompt tickets with evals, A/B against the previous version, an LLM prompt reviewer and an HTML review page for the owner; a night queue with a hard stop and a morning report; pacing against the 5-hour usage window; experimental worker sessions; an e2e phase replaying real (consented, anonymised) dialogues with a judge from another model family; and a program of several runs. Version ls.2 makes big projects first-class: a prior-art stage that decides per part what to take ready-made (licenses and liveness verified against GitHub, not recalled); an architecture stage where an architect and an independent critic iterate until a score computed by the tool reaches 9 of 10 with no criterion under 8, confirmed by a second blind critic; a written master plan of runs with a Gantt; one report page for the whole project with a drill-down page of the owner's decisions; and the ub-mode skill loaded by every coding executor and reviewer. Rules that a long run tends to forget are enforced by `ap.py` refusals, not by prose. Trigger: `/autopilot-ls`. Tests: `python3 -m unittest discover -s tests` (130: 47 upstream + 83 new). Licence: MIT, as upstream. Get it: `git clone -b ls https://github.com/artmir-tech/autopilot-ls` — the fork lives on branch `ls`; `main` mirrors upstream.

## Версия ls.2 — большие проекты

**Поиск готового** (`phases/2a-scout.md`, `prompts/scout.md`). После брифа разведчик раскладывает манифест на части и по каждой решает: подключить библиотекой, взять кусок кода, взять проект за основу, изучить или писать самим. То, чем продукт отличается, пишем сами. Лицензию, живость и само существование проверяет `ap.py scout verify` по GitHub и реестрам пакетов, а не память модели. Чужой проект за основу — только словами владельца и после пробы.

**Разработка и аудит архитектуры** (`phases/2b-architecture.md`, `prompts/architect.md`, `prompts/architecture-critic.md`, `standards/architecture-rubric.md`). Архитектор проектирует под продукт владельца, независимый критик оценивает по 18 пунктам и проходит сценарии. Балл считает `ap.py`: нужно не меньше 9 из 10, ни один пункт не ниже 8, без блокирующих находок, и результат вслепую подтверждает второй критик. Шесть кругов, дальше решает владелец. Принятая архитектура — договор для спецификации, тасков и ревью; менять её можно только отдельным аудитом изменения; после каждого прогона код сверяется с ней.

**Чистый код** (`prompts/executor.md`, `prompts/review.md`). Кодерские таски и ревьюеры сами загружают навык `ub-mode` первым действием. Копия в проекте убрана: один текст, всегда свежий. Контракт исполнителя подтверждает загрузку.

**Весь проект — заранее и на диске** (`phases/0-program.md`). Большой проект сначала становится мастер-планом: прогоны, зависимости, размер, сроки, ключевые моменты, отдельный бриф на каждый прогон. Первая сессия кода не пишет и заканчивается планом.

**Отчёт по всему проекту и страница решений** (`report/`, `ap.py project`, `question`, `manual`). Страница показывает общий процент, гант по прогонам, оценку архитектуры, что взято готовым, отчёт каждого прогона с его планом по волнам. Из неё открывается страница решений: у каждого вопроса контекст, на что соглашаешься, рекомендация, что будет при молчании, кнопка «ок» или свой вариант. Числа считает скрипт, простые слова проверяет `project lint`.

## Как поставить и проверить

Репозиторий форка: https://github.com/artmir-tech/autopilot-ls, ветка `ls` (`main` — нетронутый upstream).

```bash
git clone -b ls https://github.com/artmir-tech/autopilot-ls && cd autopilot-ls
tools/install-ls.sh                          # копия skills/autopilot → ~/.claude/skills/autopilot-ls/
python3 -m unittest discover -s tests        # 130 тестов
python3 tools/lint-ls.py                     # каждая ссылка на файл навыка существует
```

Запуск в Claude Code — `/autopilot-ls <бриф>`; без слов — продолжение прерванной сборки. Стандарт чистого кода — навык `ub-mode`: `tools/install-ls.sh` ставит его сам, если его ещё нет. Установленный рядом upstream-навык `autopilot` не мешает: другое имя, другой каталог, свои инструменты.

## Что улучшено

**Исполнители и модели**
- **Модель и усилие на таск** (`phases/4-plan.md`): поля `Тип`, `Модель`, `Усилие`, `Внимание`, `Ночью` в шапке таска; эвристика по ядру таска — схема, автомат, архитектура и промпты → `opus · high`; CRUD и адаптеры → `sonnet · medium`; переименования и docs → `haiku · low`. Ревьюеры и проверяющие G2/G4 — фиксированные модели.
- **Лестница моделей при ретраях** (`phases/5-repair.md`): `haiku·low → sonnet·medium → opus·high → opus·xhigh`; ретрай «с изменённым подходом» идёт на ступень выше; `ap.py ticket … retry` сам печатает ступень и записывает каждую попытку в `attempts`.
- **Worktree на исполнителя** (`phases/5-subagents.md`): `isolation: "worktree"`, исполнитель коммитит маленькими коммитами в своей ветке, оркестратор закрывает ветку только файлами контракта (никогда `git add -A`), делает rebase, прогон и гейты на этом дереве и вливает серию `merge --ff-only`. Чужие правки параллельного таска в коммит больше не попадают.
- **Маршрут `DONE_WITH_CONCERNS`**: это `DONE` плюс записи в `concerns`, коммит не блокирует.

**Стандарт кода и гейты**
- **ub-mode в исполнителе** (`prompts/executor.md`): обязателен целиком, кроме «Push to the main line» (вливает и пушит только оркестратор с разрешения владельца) и «Keep a Log → report» (лог в `.autopilot/<папка>/logs/NN.md`, в контракте — путь). Цикл таска: red → green → make it right → зелёный прогон.
- **Детерминированные гейты** (`standards/gates.md`): `make gates CHANGED=1` — CRAP < 10, дубли < 0.8, ни одного выжившего мутанта; красный гейт — `BLOCKING` и дозапрос, как красный тест. Полный прогон мутаций — ночью.
- **Ревью** (`prompts/review.md`, `phases/6-review.md`): вывод гейтов — факт, а не находка; ревьюер судит то, чего машина не видит (Model the Domain, Boundary Discipline, типы, идемпотентность, Fix Root Causes); мини-ось безопасности бота: текст автора в промпте только как данные, авторизация Telegram по `from.id`, секреты, персональные данные в логах. Ревью ветки — две половины: Spec + безопасность на opus, Craft на sonnet.

**Промпты как продукт**
- **Промпт-таски** (`phases/5-prompts.md`, `prompts/prompt-executor.md`, `prompts/prompt-review.md`): зона `prompts/**` только у них; файл `prompts/<stage>/<name>.xml` с `<meta>` (version, stage, model_hint), `registry.yaml`, CHANGELOG, каждое изменение — новая версия. Приёмка: XML разбирается парсером, линт обязательных секций, бюджет токенов, eval по кассетам, A/B против прошлой версии без регрессий; живые прогоны — только под капом `EVAL_MAX_USD`. Ось ревью «Prompt craft»: противоречия, двусмысленность, утечка few-shot, устойчивость к инъекции, контракт выхода, русский стиль, длина.
- **Утверждение владельцем — комбинированная схема**: сначала LLM-ревьюер сверяет требования, текст и технику; затем владельцу уходит не сырой XML, а **HTML-страница обзора** `prompt-reviews/NN-<slug>.html` — что изменилось по секциям, почему (требования с цитатами), как проверялось, открытые вопросы и поля для комментариев (один файл, по-русски, без внешних ресурсов). Таск ждёт в статусе `awaiting_owner`; сдаётся только словами владельца, его комментарии становятся дозапросом.
- **Методика — решение владельца** (`phases/2-briefing.md`): что спрашивает коуч, сколько вопросов, структура черновиков, тексты промптов, критерии рубрик не выдумываются; в режиме `full` — `ASSUMPTION` и видимая метка `[МЕТОДИКА — подтверди]`; такие таски — `Внимание: owner` и не идут ночью.

**Ночь, лимиты, сессии, программа**
- **Ночная очередь** (`phases/5-night.md`): признак «Ночью: да» вычисляется из пяти условий; ночью летит только очередь, жёсткий стоп после первого упавшего таска; утренний отчёт `night-<дата>.md` по-русски («сделано / упало / нужно от тебя / цифры»); запуск — локальная запланированная задача Claude Code Desktop, создаётся с разрешения владельца.
- **Пейсинг по окну лимитов** (`phases/5-subagents.md`, «Pacing»): данные `get_usage` в `state.js.pacing`; таск запускается, только если его оценка ≤ 0,8 остатка окна при резерве 15 %; окно > 60 % — не больше двух в полёте; ≥ 85 % — стоп и «продолжить» на время сброса. Ночью — пауза до сброса и жёсткий стоп по доле недельного лимита.
- **Воркеры-сессии** (`phases/5-sessions.md`, экспериментально): исполнитель — отдельная сессия Claude Code в своём worktree; контракт в `status/NN.json`, доска `board.json`; сессия с `role: worker` никогда не стартует прогон.
- **Программа из нескольких прогонов** (`phases/0-program.md`): `.autopilot/program.md` — прогоны с зависимостями; `ap.py program` называет следующий; образец на 7 прогонов — `examples/ls-core-program.md`.

**Приёмка и данные**
- **E2E-фаза** (`phases/8a-e2e.md`) между слепой приёмкой и отчётом: L0 — чистое ядро, L1 — стадии на кассетах (в каждом таске), L2 — replay реальных диалогов через CLI-канал на живых моделях, судья другой семьи моделей, 3 повтора, пороги по среднему и разбросу, кап `E2E_MAX_USD`; регрессия L2 становится таском.
- **Персональные данные** (`phases/1-manifest.md`): redaction gate расширен на фикстуры — имена, телефоны, `@username`, компании, города обезличиваются до коммита; в git попадают только диалоги людей, согласившихся на это, остальные живут локально вне git.

**Инструменты**
- **`ap.py` держит правила отказом**: G3 проверяет поля таска, зоны промптов, одиночество миграции в волне, «ночь» при открытых вопросах; `ticket start` отказывает ночью вне очереди, после падения и при окне ≥ 85 %; `done` из `awaiting_owner` — только словами владельца. Новые команды: `ls-check`, `queue`, `night`, `pacing`, `e2e`, `program`, `ticket … await`.
- **Русские слова форка** — по одному на понятие (таблица в `SKILL.md`): Ночь, Ночная очередь, Окно лимитов, Проверки качества, промпт-таск, Прогон диалогов, ждёт тебя, обзор промпта, Программа.
- `tools/install-ls.sh` (установка), `tools/lint-ls.py` (ссылки на файлы), `skills/autopilot/tools/measure-run.py` (замер прогона — теперь внутри навыка).

Стартовый контекст Фазы 0 вырос примерно на 5 КБ (≈ 1,3K токенов); новые файлы фаз читаются только при надобности.

## Тестовый полёт 2026-11-07 — что нашёл форк на себе

Форк прогнан целиком (`full`, глубина normal) на игрушечном проекте: консольный трекер привычек на Python и SQLite с одним prompt-требованием. Три таска плюс F1 из ревью ветки, волна 2 — как ночная очередь. Итог: всё построено, слепая приёмка 11 из 11, сдача правильно остановлена на «ждёт владельца». Дефекты форка, найденные и починенные по ходу:

| Что сломалось | Правка |
|---|---|
| `get_usage` на тарифе отдаёт только недельные окна — пейсинг вокруг 5-часового окна нечем кормить | `ap.py`: если окна 5 ч нет, темп по неделе (80 % — двое, 95 % — стоп), `--weekly-reset` |
| Worktree исполнителей режутся из репозитория папки сессии | `5-subagents.md`: оркестратор сидит в корне проекта и не уходит из него `cd` |
| Исполнитель не может писать за пределы своего worktree — лог ub-mode в основной копии не записать | лог в `.autopilot/<папка>/logs/NN.md` worktree, оркестратор переносит его на шаге 2 |
| Двум из трёх исполнителей среда отклонила команды со словом `eval` | команда кейсов — `make cases`, отклонённую команду не обходить, а называть |
| Очередь считала таск на точечном ревью несданным — ночь из зависимых не собиралась | «влит» = `done` или `review` с коммитом |
| В итоги ночи попало закрытие ревью дневного таска | ночь считает только таски своей очереди |
| A/B не определён для первой версии и для текстов без модели | `5-prompts.md`: «нет прошлой версии» — базовая линия; `model_hint: none` — все проверки детерминированные |
| Сводка гейтов давала зелёный при пустом разборе; A/B с неизвестным коммитом молча «нет прошлой версии» | `standards/gates.md`, `5-prompts.md`: молчание — красный, неизвестный коммит — ошибка, клоны закреплены |
| Исполнитель сменил систему сборки без `BLOCKED` | шаг 2 посадки сверяет изменённые манифесты зависимостей с «Решениями» (`D##` или дозапрос) |
| «Конец сборки» не знал статуса `awaiting_owner` | такой таск не держит ревью ветки, держит только `finish` |
| Мутаторы нескольких сессий перегрели ноутбук без вентилятора (средняя нагрузка ~100) | гейты бережут машину: мутатор только по изменённым файлам, воркеров `MUTATE_WORKERS` (по умолчанию — число ядер, синоним `LS_GATES_JOBS`), цель `gates-wait` ждёт, пока процессов pytest не больше 8 и нет чужого мутатора; гейты двух тасков — по очереди; полный прогон — ночью в одиночку. Счёт через `pgrep -f … \| wc -l \| tr -d ' '`: у macOS `pgrep` нет `-c` |

Что сработало как задумано: фильтр пути шаблона, `ls-check`, G2 и G3, `isolation: "worktree"` (путь и ветку harness отдаёт сам), гейты unclebob (CRAP, дубли, мутанты; флаги совпали с README), закрытие ветки по файлам и `merge --ff-only` на сдвинувшуюся основную ветку, точечное ревью и две половины ревью ветки, F1, перепроверка ремонта, HTML-страница обзора владельцу и статус `awaiting_owner`, слепая приёмка из чистого клона, отказ `finish` без слова владельца.

## Решения, принятые без владельца

1. **Основа — upstream 2.2.3**, а не более старое зеркало: правки перенесены на новую структуру (таблица выше).
2. **Исполнитель коммитит сам в своей ветке worktree** (ub-mode: «Commit often»), оркестратор вливает серию `--ff-only`; «один коммит на таск» стал «одна непрерывная серия на таск» с записанной базой. Без worktree исполнитель не коммитит — вынужденное третье исключение из ub-mode.
3. **Ретрай 1 — на той же ступени** (haiku поднимается до sonnet), **ретрай 2 — на ступень выше**; выше `opus·xhigh` — только `max` словами владельца.
4. **Ревью ветки — две половины параллельно** (Spec + безопасность на opus, Craft на sonnet) — так правило «Craft-ревьюер на sonnet» ложится на upstream, где ревьюер один; +1 субагент на прогон.
5. **Безопасность — у opus-половины**, не у Craft на sonnet: цена пропуска выше.
6. **Каждый промпт-таск проходит отдельное ревью** — осознанное расширение правила стоимости upstream.
7. **Страницу обзора для владельца пишет промпт-ревьюер** — это его единственная запись; при `BLOCKING` страницы нет. Влитый промпт-таск ждёт владельца, не блокируя остальную сборку; ночью зависимые от него таски не летят.
8. **Линт промптов по умолчанию** выведен из существующих промптов стадий проекта: корень `prompt_system`, `<meta>` (version, stage, model_hint — атрибутами или дочерними элементами), секции данных, вывода со схемой и защиты; проект переопределяет в `prompts/lint.yaml`.
9. **Пустой `EVAL_MAX_USD` / `E2E_MAX_USD` = живые прогоны выключены**: деньги — решение владельца, умолчаний нет.
10. **Промпт-исполнителю `.env` копируется в worktree нераскрытым**, как слепому проверяющему в upstream: иначе живой eval невозможен.
11. **Числа пейсинга до калибровки**: оценки 2 / 5 / 10 / 14 % окна по ступеням, резерв 15 %, ночная доля недели по умолчанию 15 % (владелец ставит свою командой `ap.py pacing --night-weekly-max-pct`).
12. **Ночь при 85 % окна встаёт на паузу** до сброса, а при недельной доле и первом падении — останавливается совсем.
13. **Запланированные задачи** (ночная, «продолжить после сброса», следующий прогон программы) — постоянная настройка: вопрос владельцу один раз, ответ записывается в «Договорились».
14. **`ap.py` проверяет правила отказом** там, где проверка механическая; остальное — суждение оркестратора.
15. ~~Оркестратору разрешено писать копию `docs/standards/ub-mode.md`~~ — отменено в ls.2: копии больше нет, исполнители грузят навык.
16. **`7-instruments.md` создан заново** как справочник данных форка и читается по необходимости — принцип «один файл фазы за раз» сохранён.
17. **`night_ok` — snake_case**, как в постановке, хотя upstream пишет поля в camelCase.
18. **Воркеры-сессии — только по словам владельца и никогда ночью**: приложение не стартует сессии из хода, начатого задачей по расписанию; контракт воркера — файл, потому что отчёт сессии доходит обрезанным.
